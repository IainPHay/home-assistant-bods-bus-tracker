# v0.7 beta development record

This document tracks the v0.7 beta series while stable v0.6.0 remains available to normal HACS users.

The v0.7 branch starts from stable v0.6.0. The conservative live-to-GTFS ETA/matching policy remains unchanged unless a later beta explicitly targets it.

## Beta strategy

- Development branch: `feature/v0.7`
- First beta version: `0.7.0-beta.1`
- Stable v0.6.0 remains the recommended release for general testing.
- v0.7 prereleases are for targeted beta testing.
- Wiki review and v0.6 automation testing can continue independently.

## 0.7.0-beta.1 — provider-portability foundation

The first beta is deliberately small and low risk.

### Public stop coordinates

The native **Next bus** entity already exposes a `stop` attribute containing the monitored ATCO code and name.

Beta.1 adds the public GTFS boarding-point coordinates when they are available:

```yaml
stop:
  atco: "..."
  name: "..."
  latitude: 55.123456
  longitude: -1.123456
```

This is intended to make external pedestrian-routing providers easier to configure without manually looking up stop coordinates.

Only the public bus-stop coordinates are exposed. Person/device coordinates remain outside BODS Bus Tracker.

If no usable GTFS stop metadata are available, the existing `atco` and `name` keys remain unchanged and no coordinates are invented.

## Routing-provider investigation

The BODS runtime remains provider-neutral: it consumes a Home Assistant duration sensor in seconds, minutes or hours.

### HERE Travel Time

Status: **reference provider / already live-validated**

- Home Assistant Core integration.
- Supports pedestrian routing.
- Supports dynamic entity origins such as `person` / `device_tracker`.
- HOME Assistant currently documents a HERE Base Plan allowance of 5,000 free transactions per month.
- v0.6 was validated end-to-end using HERE.

Reference:

https://www.home-assistant.io/integrations/here_travel_time/

### Google Maps Travel Time

Status: **viable alternative, but not the preferred free option**

- Home Assistant Core integration.
- Supports walking routes and dynamic Home Assistant locations.
- Requires Google billing to be enabled.
- Home Assistant currently documents 5,000 free Compute Routes Pro requests per month.

Reference:

https://www.home-assistant.io/integrations/google_travel_time/

### Waze Travel Time

Status: **not suitable for BODS walking guidance**

- Home Assistant Core integration.
- Supports dynamic Home Assistant origin/destination entities.
- Intended for road travel rather than pedestrian routing.

Reference:

https://www.home-assistant.io/integrations/waze_travel_time/

### openrouteservice

Status: **promising routing backend; Home Assistant integration path needs new work**

Reasons it is interesting:

- walking/foot routing;
- OpenStreetMap-based;
- public hosted API;
- self-hostable backend;
- substantially larger published free request allowance than the current HERE/Google monthly allowance.

References:

https://openrouteservice.org/
https://openrouteservice.org/services/
https://openrouteservice.org/restrictions/

Important 2026 caveat:

The older HACS custom component `eifinger/open_route_service` is archived and explicitly no longer maintained.

https://github.com/eifinger/open_route_service

In addition, openrouteservice has deprecated the old `api.openrouteservice.org` API host in favour of `api.heigit.org`, with shutdown of the deprecated host announced for 2026-09-28.

Therefore v0.7 should **not** simply recommend the archived HACS integration.

### Current preferred direction

The openrouteservice work is now being split into a **standalone Home Assistant/HACS integration project** rather than being implemented inside BODS Bus Tracker.

A temporary bootstrap branch exists at `project/openrouteservice-hacs` with the proposed architecture. The intended end state is a separate repository and custom integration in its own right.

Do not put openrouteservice API credentials or direct provider calls inside the BODS ETA/matching engine.

The companion/provider layer should ideally:

- create a normal Home Assistant duration sensor;
- accept a `person` or `device_tracker` as dynamic origin;
- accept fixed bus-stop coordinates as destination;
- use walking/foot mode;
- control its own polling and quota;
- keep API credentials outside BODS Bus Tracker;
- expose predictable duration units and unavailable/error semantics.

## 0.7.0-beta.2 — catchable-bus state

Beta.2 starts the second roadmap workstream by creating trusted, inspectable catchability state **before** building the zone-exit automation.

### Calculation

For departure and combined stop views:

```text
required lead time = effective walking minutes + configured safety margin

first catchable departure = first ordered departure where:
expected departure >= now + required lead time
```

The calculation deliberately uses the existing passenger-facing `expected` time, falling back to `scheduled` only if necessary. That means a genuine live delay can make a bus catchable without changing the underlying BODS matching policy.

### New configuration

Per stop:

- **Catchable-bus safety margin**
- default: **0 minutes**
- range: **0–30 minutes**

A zero default means "conceivably catchable" is literal: the bus is reachable if the effective walking duration fits before departure. Users who want a more conservative policy can add an explicit margin.

### New state

A **Catchable bus** sensor exposes:

- the first catchable route as its state;
- effective walking minutes;
- configured margin;
- required total lead time;
- a privacy-safe summary of the catchable departure;
- a privacy-safe summary of the immediately following departure.

The summaries do not copy live vehicle latitude/longitude or trip IDs.

### Safety / architecture

- Catchability does not alter `Next bus`, ETA, matching or departure ordering.
- Routed/static walking resolution still happens first.
- Walking disabled -> catchable state disabled.
- Arrivals-only stop view -> catchable state disabled.
- The integration evaluates the complete ordered departure set internally rather than only the first 12 rows exposed to dashboards.
- No zone-exit automation is added until this state has been validated in real Home Assistant use.

### Real Home Assistant validation checklist

Before adding the zone-exit blueprint, beta.2 should be checked in a real installation:

1. Reconfigure a departure stop with a non-zero static or routed walking time and **Catchable-bus safety margin = 0**.
2. Confirm the new **Catchable bus** entity selects the first departure whose expected time is at least the effective walking duration away.
3. Set the margin to **2 minutes** and confirm a marginal departure is skipped when necessary.
4. Confirm the sensor exposes the selected departure plus the immediately following departure.
5. If a live delay occurs, verify a delayed departure can become catchable when its BODS expected time moves later.
6. Make the routed walking provider unavailable and confirm catchability follows the existing static walking fallback rather than changing ETA/matching.
7. Restore the routed provider and confirm dynamic walking and catchability recover without reconfiguration.
8. Confirm Arrivals-only view does not expose a catchable departure.
9. Download diagnostics and confirm no person/device coordinates, routing credentials, live vehicle coordinates or trip IDs are copied into the catchable summary.
10. Confirm existing **Next bus**, **Leave by**, **Leave in** and **Leave now** behaviour is unchanged.

Record the observed catchable route, effective walking minutes, safety margin, expected departure and following departure for at least one natural live-data example.

## 0.7.0-beta.3 — diagnostics/privacy hardening

Beta.3 is a focused corrective prerelease following real Home Assistant beta.2 diagnostics testing.

The beta.2 diagnostics capture revealed that the private complete departure sequence used internally for catchability could remain in coordinator state when walking guidance was disabled. The normal catchable path removed the scratch key, but the `walking_disabled` path returned before cleanup. Home Assistant diagnostics could therefore include `_departures_for_guidance`, including internal candidate details such as trip IDs.

Beta.3 fixes this in two independent layers:

- catchability now removes `_departures_for_guidance` before every return path;
- diagnostics also strip the private scratch key defensively, even if a future coordinator regression were to reintroduce it.

Regression tests cover both protections.

The beta.2 capture did **not** show a `person` / `device_tracker` coordinate leak or routing-provider credential leak. Public bus-stop coordinates remain safe to expose in normal entity state, while diagnostics continue stripping latitude/longitude fields.

### Beta.3 real Home Assistant validation

After installing beta.3:

1. Keep at least one stop with walking guidance disabled and one with catchable walking enabled.
2. Download BODS diagnostics.
3. Confirm `_departures_for_guidance` is absent everywhere.
4. Confirm catchable summaries still contain no latitude, longitude or trip ID.
5. Confirm no `person` / `device_tracker` coordinates or routing-provider credentials appear.
6. Confirm public stop operation, Next bus, Leave by/in/now and Catchable bus remain unchanged.

### Beta.3 validation result — passed 2026-09-13

Real Home Assistant 2026.9.2 diagnostics on `0.7.0-beta.3` confirmed the privacy fix:

- `_departures_for_guidance` is absent from the complete diagnostics payload;
- latitude/longitude fields are absent from BODS diagnostics;
- no `person` / `device_tracker` coordinates are copied into BODS diagnostics;
- the BODS API key remains redacted;
- the Haymarket `walking_disabled` path now exposes only the intended catchable summary and no private scratch departure list;
- the Fairway catchable state retains its explicit 5-minute walking time + 3-minute margin = 8-minute required lead policy.

That closes the beta.3 privacy gate.

## 0.7.0-beta.4 — zone-exit catchable-bus notification

Beta.4 starts the automation layer now that catchability has passed real Home Assistant validation.

### Blueprint design

The new **Zone exit catchable bus notification** blueprint:

- triggers when a selected Home Assistant `person` leaves a selected `zone`;
- reads the native BODS **Catchable bus** sensor;
- only proceeds when the sensor reports `status: ok`;
- never recalculates which bus is reachable;
- never reads the private full departure scratch list;
- uses the walking time, safety margin and selected/following departures already exposed by BODS;
- provides one required primary notification/announcement action and one optional second action;
- exposes a ready-to-send `bods_message` plus structured `bods_*` variables for customised actions.

The generated message preserves route, destination, expected/scheduled departure time, live/timetable source, timing/delay detail, walking duration, explicit margin, required lead time and the following departure.

The blueprint deliberately has **no separate margin input**. Catchability policy stays configured on the BODS stop so the automation cannot silently disagree with the integration.

Documentation: [`ZONE_EXIT_NOTIFICATION.md`](ZONE_EXIT_NOTIFICATION.md)

Concrete example: [`example_zone_exit_catchable_notification.yaml`](example_zone_exit_catchable_notification.yaml)

### Beta.4 real Home Assistant validation checklist

Before beta.4 is published:

1. Import the zone-exit blueprint into a real Home Assistant installation.
2. Configure a person, origin zone, Catchable bus sensor and primary Companion App notification.
3. Confirm a zone exit with `status: ok` sends exactly one message.
4. Compare the notified route, destination, expected/scheduled times, walking time, safety margin and following departure with the native Catchable bus entity.
5. Validate a genuinely live/delayed departure.
6. Validate timetable fallback.
7. Confirm `walking_disabled`, `no_departures` and `none_in_window` do not produce a misleading notification.
8. Configure the optional second action and confirm both recipients receive the same trusted journey data.
9. Confirm existing Next bus / Leave by / Leave in / Leave now behaviour remains unchanged.

### Controlled Home Assistant validation — passed 2026-09-14

A real Home Assistant automation was created from the blueprint using a person, origin zone, Haymarket Catchable bus sensor and Companion App notification action.

A controlled **Run actions** trace confirmed:

- Catchable bus resolved with `status: ok`;
- X15 was selected as the first catchable departure and X16 as the following departure;
- effective walking was 34 minutes with margin 0 and required lead 34;
- timetable-fallback data was preserved correctly;
- all `bods_*` variables were populated;
- `notify.mobile_app_...` was invoked successfully;
- the automation completed normally.

The first trace exposed only cosmetic whitespace around separators. The message assembly was then rewritten to deterministic fragments and a second trace produced clean output:

```text
Catchable: X15 to Bus Station — expected 14:38; scheduled 14:38 · 36 min away · timetable. Walking: 34 min (34 min required lead). Following: X16 to Bus Station — expected 14:53; scheduled 14:53 · timetable.
```

Because **Run actions** bypasses the trigger, a genuine zone transition was still required.

A subsequent physical zone exit on 2026-09-14 confirmed the configured Home Assistant `zone` / `leave` trigger fires correctly. The same trace exposed a condition bug before the notify action: the valid-data template could finish by returning the selected departure timestamp string instead of an explicit boolean true. The blueprint condition has therefore been corrected to render only boolean route/time validity checks, with regression coverage using representative catchable data.

The remaining beta.4 live gate is now an end-to-end retest with the corrected blueprint:

1. a genuine person exit from the configured origin zone with Catchable bus `status: ok`;
2. exactly one notification action;
3. confirmation that the target phone receives the notification.

Only after that should the blueprint be promoted into the next prerelease.

## Design constraints

- State must be trusted before behaviour is automated.
- Walking/routing must remain downstream of ETA/matching.
- Provider credentials must not enter BODS diagnostics.
- Person/device coordinates must not be copied into BODS attributes or diagnostics.
- Public bus-stop coordinates are safe to expose and are useful for provider setup.
- Stable v0.6.0 remains available while v0.7 beta work proceeds.
