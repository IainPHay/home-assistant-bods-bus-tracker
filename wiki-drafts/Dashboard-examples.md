# Dashboard examples

BODS Bus Tracker includes two stock Home Assistant **Markdown** dashboard cards:

- an ordinary departure board for a normal boarding stop;
- a terminus/bus-station card for stops configured as **Arrivals and departures**.

No custom frontend card is required.

The repository YAML is canonical:

- [Ordinary departure card](https://github.com/IainPHay/home-assistant-bods-bus-tracker/blob/main/example_dashboard_card.yaml)
- [Terminus arrivals/departures card](https://github.com/IainPHay/home-assistant-bods-bus-tracker/blob/main/example_terminus_card.yaml)

Home Assistant's Markdown card supports templates and an `entity_id` list so the card refreshes when the referenced entity changes:

https://www.home-assistant.io/dashboards/markdown/

## Ordinary departure board

Use this for a stop configured as **Departures**.

![Example BODS Bus Tracker departure card](https://raw.githubusercontent.com/IainPHay/home-assistant-bods-bus-tracker/main/docs/images/departure-card.png)

### Install it

1. In Home Assistant go to **Settings → Devices & services → BODS Bus Tracker**.
2. Open the required bus-stop device.
3. Find its **Next bus** entity and copy the entity ID.
4. Open the dashboard you want to edit.
5. Add a **Markdown** card.
6. Open the card's code editor.
7. Copy the complete YAML from [`example_dashboard_card.yaml`](https://github.com/IainPHay/home-assistant-bods-bus-tracker/blob/main/example_dashboard_card.yaml).
8. Replace **both** occurrences of:

   ```text
   sensor.YOUR_NEXT_BUS_ENTITY
   ```

   with your own native **Next bus** entity ID.
9. Save the card.

The exact entity ID is generated by Home Assistant and will differ between installations.

### Why the entity ID appears twice

The example contains both:

```yaml
entity_id:
  - sensor.YOUR_NEXT_BUS_ENTITY
```

and:

```jinja
{% set entity = 'sensor.YOUR_NEXT_BUS_ENTITY' %}
```

The first tells the Markdown card which Home Assistant state should cause the template to refresh. The second is the entity the Jinja template actually reads.

Replace both.

## What the ordinary card shows

The headline row displays the next boardable departure, including:

- route;
- minutes until due;
- destination where available;
- expected time;
- **Live** or **Timetable** source;
- early/on-time/late information;
- vehicle ID when a live vehicle is matched.

The table below shows the next five departures by default.

The footer shows tracker health, the number of live-tracked rows and how recently the tracker updated.

### Live versus timetable

The stock card uses:

- 🟢 **Live** — a trustworthy live vehicle has been matched to the timetable journey;
- 🕒 **Timetable** — the published timetable is being used for that journey.

A timetable row does **not** necessarily indicate a BODS outage.

It is completely valid for:

```text
Data status: OK
Departure source: Timetable
```

to occur at the same time. That means the live feed is healthy but that particular journey has not yet been matched to a live vehicle.

## Walking guidance on the card

If walking guidance is configured, the card can show:

```text
🚶 Leave in 7 min · leave by 10:24
```

or:

```text
🚶 Leave now · 9 min walk
```

The card is **provider-neutral**.

It does not know whether the effective walking time came from:

- static walking time;
- HERE Travel Time;
- another compatible duration provider;
- static fallback because routed walking is temporarily unavailable.

BODS Bus Tracker resolves the effective walking state first; the card simply displays the resulting `walking_minutes`, `leave_by`, `leave_in_minutes` and `leave_now` attributes.

For HERE setup see [Setting up routed walking with HERE Travel Time](Setting-up-HERE-Travel-Time).

## Change the number of departures

The ordinary example contains:

```jinja
{% for row in departures[:5] %}
```

To show three departures instead:

```jinja
{% for row in departures[:3] %}
```

To show eight:

```jinja
{% for row in departures[:8] %}
```

Five is the recommended default because it keeps the card compact.

The BODS integration normally exposes more rows in the live `departures` attribute; the card chooses how many to display.

## Terminus / bus-station card

Use the terminus card only for a stop configured as:

**Arrivals and departures**

The canonical YAML is:

[`example_terminus_card.yaml`](https://github.com/IainPHay/home-assistant-bods-bus-tracker/blob/main/example_terminus_card.yaml)

Install it the same way as the ordinary card and replace both occurrences of:

```text
sensor.YOUR_NEXT_BUS_ENTITY
```

with the terminus **Next bus** entity.

The terminus card can show:

- **At stand** outbound vehicles;
- **Approaching** inbound terminating journeys;
- **Arrived** vehicles;
- separate departure and arrival tables;
- `previous_stop` context;
- walking guidance for the next **boardable departure**;
- live/timetable source and tracker health.

The integration deliberately does **not** assume that an arriving vehicle forms a later outbound service.

See [Terminus setup](Terminus-setup) for the matching rules and recommended configuration.

## Card behaviour during live-data problems

The cards remain useful during an upstream live-data problem because timetable departures remain available.

The footer can show:

- **Tracker updating** — normal;
- **Live data degraded** — some live requests failed;
- **Timetable data only** — all current live requests failed and timetable fallback is being used.

If a card continues to show timetable departures during a BODS outage, that is expected resilience rather than a failure of the dashboard.

See [Troubleshooting live data](Troubleshooting-live-data).

## Common problems

### Card says "No upcoming buses"

Check the native **Next bus** entity first.

If its `departures` attribute is empty, the card has nothing to display. Check:

- the selected services;
- the physical stop/direction;
- time of day;
- BODS timetable availability.

### Card does not refresh

Confirm that both placeholder entity IDs were replaced and that the `entity_id:` entry refers to the same native **Next bus** entity used in the template.

### Template error after copying

Copy the **complete** YAML file rather than only the `content:` block. YAML indentation is significant.

### Terminus status never appears

Not every operator publishes enough live information for **At stand**, **Approaching** or **Arrived** to be proven.

The integration intentionally prefers no status to inventing an unreliable vehicle link.

## Advanced dashboard ideas

Because the rich `departures`, `arrivals` and `terminus` attributes remain available in Home Assistant's live state machine, users can build other cards or templates without changing BODS Bus Tracker.

When creating custom templates:

- prefer `row.get(...)` for optional fields;
- assume an individual journey may be timetable-only;
- do not infer that an incoming terminus vehicle forms an outgoing journey;
- use `walking_minutes` rather than assuming a particular routing provider.

The large rolling journey attributes are intentionally excluded from Recorder history, but remain available to live dashboard templates and automations.
