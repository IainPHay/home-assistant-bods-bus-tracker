# v0.6 validation record

This document is the durable validation record for the BODS Bus Tracker v0.6 development series. It records automated validation, real Home Assistant testing, bugs found during beta testing, fixes applied, and the remaining criteria for stable v0.6.0.

## Scope of v0.6

v0.6 combines four substantial changes:

1. provider-neutral routed dynamic walking time;
2. shared/rate-limited BODS live-feed acquisition;
3. shared and persistent GTFS startup/index optimisation;
4. Home Assistant quality-scale hardening, including native tests, Repairs and strict typing.

The live-to-GTFS ETA matching policy remains deliberately conservative and is not rewritten by the dynamic walking work.

## Beta.1 — UI architecture

Validated in real Home Assistant:

- the integration is declared `single_config_entry`;
- the redundant **Add hub** path is removed;
- **Add bus stop** remains available;
- existing multi-stop/subentry behaviour remains intact.

## Beta.2 — shared BODS live feed and auth handling

A real-world false reauthentication event exposed excessive request volume from the old architecture and from the retained standalone Fairway MQTT tracker.

Changes validated:

- one shared account-level BODS client;
- operator-filtered SIRI-VM feed reused across configured stops;
- route filtering is local;
- successful and failed operator responses cached for 15 seconds;
- concurrent same-operator requests de-duplicated;
- real upstream request starts serialised with at least 6 seconds between starts;
- only HTTP 401 triggers reauthentication;
- HTTP 403 is `access_forbidden`;
- HTTP 429 is `rate_limited`;
- timeout/connection errors fall back without invalidating credentials;
- the native numeric delay sensor is unavailable when no live delay exists instead of exposing a non-numeric state.

The legacy standalone `fairway-bus.service` was disabled before validation so it could not continue generating four route-level BODS requests per cycle.

Real diagnostics confirmed the shared feed returned the configured Fairway/Haymarket services, live matching was healthy, and the existing API key worked without a false reauth flow.

## Beta.3 — GTFS startup optimisation

Beta.2 diagnostics measured approximately 250.5 seconds for config-entry setup because Fairway and Haymarket independently parsed the same North East regional `stop_times.txt`.

Beta.3 changed this to:

- one shared per-region parsed GTFS index;
- union of configured services per region;
- lightweight per-stop filtering from the shared index;
- persistent JSON parsed-index cache;
- strict cache key based on GTFS fingerprint, service date, exact service set and cache schema;
- no pickle or executable cache format.

Real Home Assistant validation:

- first beta.3 restart rebuilt one shared North East index and populated both stops;
- first rebuild setup was approximately 106.6 seconds, down from the ~250.5 second beta.2 baseline;
- a subsequent same-day restart restored the parsed index from disk in approximately 0.964 seconds;
- later beta.4 diagnostics showed gross config-entry setup around 42.1 seconds, of which about 39.7 seconds was Home Assistant platform-import waiting; actual BODS integration work was about 2.4 seconds;
- Fairway restored the shared index from disk in about 0.137 seconds and Haymarket reused it from memory;
- live BODS/GTFS matching remained healthy.

Automated cache-policy tests prove that GTFS fingerprint, service date, service set and schema changes invalidate the persistent parsed cache.

## Beta.5 — reconfigure-flow performance

During the beta.4 Repair test, opening an existing stop's **Reconfigure** flow took long enough to fail.

Root cause:

- `discover_stop_services()` rescanned the regional `stop_times.txt`;
- it CSV-parsed every row even though reconfiguration only needed rows for one stop;
- this bypassed the startup optimisation and could exceed Home Assistant's flow timing tolerance.

Beta.5 optimisation:

- raw UTF-8 `stop_times.txt` lines are first cheaply filtered for the target stop token;
- only candidate lines are CSV-parsed;
- exact `stop_id` column matching is still required;
- quoted stop IDs remain supported;
- false positives where the stop text appears in another GTFS column are rejected;
- all services calling at the stop remain selectable.

## Routed dynamic walking — behaviour already proven

Proven by automated and live testing:

- feature is opt-in per stop;
- static walking remains the fallback;
- missing configured source falls back safely;
- transient invalid source states do not crash the stop;
- seconds/minutes/hours are normalised;
- routed values are rounded up to a whole minute for leave guidance;
- values over 120 minutes are rejected;
- stale values fall back;
- arrival-only mode does not expose leave guidance;
- routing logic is downstream of ETA/matching;
- BODS Bus Tracker does not store routing-provider credentials;
- BODS Bus Tracker does not force-update the provider on every BODS poll;
- no person/device coordinates are copied into BODS walking diagnostics.
